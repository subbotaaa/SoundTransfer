# SoundTransfer (`st`)

Передача звука **с одного устройства на другое** по локальной сети с минимальной задержкой.
Один бинарник на Rust: любая сторона может быть отправителем или приёмником — режим
выбирается в приложении и сохраняется. Работает в любой комбинации: два Windows,
два Mac или смешанная пара.

Захват на Windows отдаёт весь системный микс нативно (WASAPI loopback). На macOS
нативного loopback нет — отправитель захватывает входное устройство; для передачи
системного звука установите виртуальный кабель (например, [BlackHole](https://github.com/ExistentialAudio/BlackHole)),
направьте в него вывод системы (или Multi-Output Device) и выберите его источником захвата.

**Запуск без аргументов (двойной клик) открывает графический интерфейс** — вкладки
«Отправка»/«Приём», поле IP, слайдер джиттер-буфера, выбор устройства, живая статистика.
CLI-режимы (`st send` / `st recv`) остаются для скриптов и автозапуска.

- Windows: ярлык **SoundTransfer** на рабочем столе (или `st.exe` двойным кликом).
- Mac: `sh make_app.sh` собирает **SoundTransfer.app** — перетащите его в «Программы»
  и запускайте как обычное приложение.

```
Устройство A (игра/музыка) ──захват──> st send ──UDP/LAN──> st recv ──вывод──> Устройство B → наушники
```

## Ожидания по задержке (честно)

| Участок | Задержка |
|---|---|
| Захват + сеть + буфер + вывод на приёмнике (наша часть) | ~25–50 мс |
| Bluetooth до AirPods (вне нашего контроля) | ещё ~150–250 мс |

Для музыки, видео и казуальных игр — нормально. Для соревновательных шутеров
подключите к приёмнику **проводные** наушники: останется только наша часть.

Каждый тег `v*` автоматически собирается в GitHub Actions: `SoundTransfer-windows.zip`
(st.exe) и `SoundTransfer-macos.zip` (SoundTransfer.app). Скачали → распаковали → готово.

Выпустить новый релиз:

```bash
git tag v0.2.0 && git push origin master --tags
```

macOS при первом запуске скачанного приложения скажет «не удаётся проверить
разработчика». Разрешите запуск: **Системные настройки → Конфиденциальность
и безопасность → «Всё равно открыть»** (кнопка появляется после первой
попытки запуска), либо снимите карантин командой:

```bash
xattr -dr com.apple.quarantine /Applications/SoundTransfer.app
```

Релизы до v0.2.1 не были подписаны даже ad-hoc, поэтому Gatekeeper показывал
«приложение повреждено» без кнопки обхода — для них поможет только `xattr`
выше. Начиная с v0.2.1 бандл подписывается ad-hoc при сборке.

## Сборка

### Windows

```powershell
cargo build --release
# бинарник: target\release\st.exe
```

Совет: если проект лежит в синхронизируемой папке (OneDrive и т.п.), вынесите
артефакты сборки наружу: `$env:CARGO_TARGET_DIR = "C:\dev\st-target"` перед сборкой.

### Mac

Кросс-компиляция Windows→macOS непрактична, поэтому собираем на самом Mac (5 минут):

```bash
# 1. Rust (если ещё нет)
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
# 2. Линкер Xcode (если ещё нет)
xcode-select --install
# 3. Скопируйте папку проекта на Mac (git clone / AirDrop / общая папка) и:
cd SoundTransfer
cargo build --release
```

При первом запуске macOS спросит про входящие соединения — нажмите **Allow**.

## Использование

**На принимающем устройстве (сначала запустить приёмник):**

```bash
./target/release/st recv
```

**На отправляющем устройстве (IP приёмника можно не указывать — найдётся по mDNS):**

```powershell
st.exe send 192.168.1.XX
```

Всё. Звук пойдёт с отправителя на приёмник. Остановка — Ctrl-C (отправитель шлёт BYE).
В GUI направление задаётся вкладками «Отправка»/«Приём» и запоминается между запусками:
кто отправитель, а кто приёмник — решаете вы, в любой комбинации ОС. Если отправитель —
Mac, выберите источником захвата виртуальный кабель (BlackHole).

### Полезные опции

```text
st recv --buffer-ms 20      # целевой джиттер-буфер: меньше = ниже задержка,
                            # больше = устойчивее к Wi-Fi (диапазон разумного: 10–60)
st recv --device "AirPods"  # вывод в конкретное устройство (подстрока имени)
st send <ip> --format f32   # без 16-битного сжатия (3.2 Мбит/с вместо 1.6)
st send <ip> --frames-per-packet 256   # крупнее пакеты (терпимее к CPU, чуть больше задержка)
st list-devices             # показать устройства вывода
st send --dump out.raw --seconds 10    # диагностика захвата: запись в файл + peak/RMS
```

## Как это работает

- **Захват:** на Windows — WASAPI loopback через cpal: устройство вывода открывается
  как вход, Windows отдаёт копию всего микса (48 кГц / f32 / стерео как правило).
  На macOS — захват входного устройства (для системного звука — виртуальный кабель).
  При тишине в системе loopback не выдаёт данных — отправитель это замечает
  и синтезирует пакеты тишины по wall-clock, чтобы приёмник не пересобирал буфер.
- **Транспорт:** UDP, сырой PCM s16le (~1.6 Мбит/с — кодек не нужен, нет его задержки).
  Пакет = 24-байтовый заголовок (magic, seq, sample_pos, формат) + 128 фреймов (2.67 мс).
- **Приёмник:** джиттер-буфер с целью 20 мс. Потерянные пакеты → тишина (тайминг
  сохраняется), поздние → drop, переполнение после Wi-Fi-затыка → срез до цели.
  Дрейф часов отправителя и приёмника компенсируется незаметным drop/dup одного фрейма
  на ~10 мс потока при уходе EMA заполненности за ±4 мс от цели.
- Раз в секунду приёмник печатает статистику: заполненность буфера, потери,
  underruns, срезы, slip. Если underruns регулярные — увеличьте `--buffer-ms`.

## Советы по сети

- Обе машины лучше держать по кабелю или на **5 ГГц** Wi-Fi.
- Спайки >20 мс в `ping <ip-приёмника>` с отправителя — причина щелчков; это Wi-Fi, не приложение.
- Порт по умолчанию **48100/UDP** (изменить: `--port` с обеих сторон).

## Замер задержки

Играйте клик-трек на отправителе, положите телефон с диктофоном между колонками
отправителя и колонками приёмника, запишите, откройте запись в Audacity и измерьте
смещение между парами щелчков. С колонками приёмника видно задержку приложения
(~цель ≤60 мс), с Bluetooth-наушниками — полную, включая Bluetooth.

## Автообнаружение (mDNS)

Приёмник анонсирует себя в локальной сети (`_soundtransfer._udp`), поэтому IP можно не вводить:

- **GUI:** кнопка «🔍 Найти» рядом с полем IP — найденный приёмник подставится сам.
- **CLI:** просто `st send` без адреса — найдёт приёмник за ~3 секунды.

Если поиск не находит приёмник (редко: multicast отключён на роутере) — вводите IP вручную, как раньше.

## Управление из Home Assistant

Приложение (в GUI-режиме) поднимает HTTP-сервер управления на порту **48101**:

```text
POST /start   — запустить передачу или приём (какой режим выбран в приложении)
POST /stop    — остановить
GET  /status  — {"running":true|false,"info":"..."}
```

Готовый конфиг переключателя — в [homeassistant.yaml](homeassistant.yaml): добавьте его
в `configuration.yaml` HA, подставьте IP отправителя и приёмника и перезапустите HA.
Появится переключатель **SoundTransfer**: включение стартует приём на одном устройстве
и отправку на другом, выключение останавливает оба.

Чтобы кнопка работала всегда, приложение должно быть запущено на обеих машинах:

- **Windows:** ярлык в автозагрузке уже создан (`shell:startup`), правило брандмауэра
  для TCP 48101 добавлено.
- **Mac:** `sh make_app.sh --autostart` — соберёт приложение, положит в /Applications
  и настроит автозапуск при входе **в скрытом виде** (только иконка в строке меню,
  LaunchAgent `local.soundtransfer`). Если раньше добавляли приложение в «Объекты
  входа» — удалите оттуда, чтобы не запускалось дважды.

Флаг `--hidden` запускает GUI со скрытым окном (только трей/строка меню) на любой
платформе. Закрытие окна тоже прячет приложение в трей; полный выход — через
пункт «Выход» в меню трея.

Отправитель при старте из HA использует сохранённый IP приёмника, а если поле пустое —
находит приёмник сам через mDNS. Сервер управления не имеет аутентификации — он рассчитан
на доверенную домашнюю сеть.
